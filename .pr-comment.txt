## 1. The call site, and the gate it sits behind

The walker now has a call site: an on-demand **"Backfill skin-temp absolutes"** button in the Test Centre's Diagnostic Tools card (the issue's "diagnostic first" + safest trigger — doing it automatically on upgrade risks a long first launch on a deep history, exactly the #1854 failure mode). The action is disabled while a pass is running and shows the result line under the button.

The gate it sits behind is NOT a new-data gate (the #1854 trap). It is a user tap. The backfill runs only when explicitly asked, so it can never be wired into a condition under which it has nothing to do — it runs precisely when there is something to do.

The walker now owns the WHOOP 4.0 window-anchor scan in a self-contained `runBackfill()` entry point, so the call site does not duplicate engine internals. It replicates the scoring pass's window-wide `skinTempSamples` read + `Whoop4SkinTemp.deviceAnchorRaw` learn (rule 3: the anchor comes from the CURRENT scoring window, never the global 826 fallback), then pages through the candidate nights until a page is empty or the page budget (10 pages × 50 nights) is reached.

## 2. Evidence the candidate nights still have raw samples

The result line is self-attesting. It reports `filled / declined / no-raw-data` counts:

```
skin-temp backfill (#1853): filled N, declined M, no raw data K (anchor from current window, reached end)
```

If `no-raw-data` equals the candidate count, the raw streams have aged out and the backfill fills nothing — the diagnostic the issue's unsettled unknown asked for, produced by the action itself rather than claimed in advance. The `noRawData` list is already collected per-night in the walker (`skin.isEmpty` → `noRawData.append(day)`), so the evidence is the run's own output, not a pre-ship assertion.

## 3. A note on the Android side

The Android twin is currently reverted, so this PR ships **Apple-only deliberately**. The pure half (`SkinTempBackfill` in StrandAnalytics) and its tests are cross-platform and already shared; the Android wiring will follow once the Android twin's call-site question is settled. Worth being deliberate about rather than incidental — agreed, and called out here so it is.
